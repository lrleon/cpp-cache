\begin{abstract}
This article presents an advanced implementation of a thread-safe cache
system in C++ that incorporates TTL (Time To Live) management with
sliding window refreshes, entry states, and a variadic API with perfect
forwarding. We detail the concurrency challenges, lock-free performance
metrics, and formal verification using advanced Promela models that 
account for locking gaps and ABA protection. The implementation has been 
validated in production, handling \textbf{100,000 requests per second} 
in a Kubernetes environment, and maintains \textbf{80\% docstring coverage}
for high maintainability.
\end{abstract}

\section{Introduction}

Cache systems are fundamental components in modern software
architectures, especially in distributed and high-performance
applications. However, implementing a thread-safe cache presents a
critical challenge that goes beyond simple data storage: \textbf{how to
handle multiple threads requesting the same key while the value is being
computed}.

\subsection{The Core Problem: Thundering Herd in Caches}

Consider a scenario where an expensive operation (database query, API
call, complex calculation) takes several seconds to complete. Without
proper coordination, multiple threads requesting the same key
simultaneously will each trigger the expensive operation:

\begin{lstlisting}[caption=Problematic behavior without coordination]
Time: T0
Thread 1: cache.get("expensive_key") -> MISS -> starts computation
Thread 2: cache.get("expensive_key") -> MISS -> starts computation  
Thread 3: cache.get("expensive_key") -> MISS -> starts computation

Result: N expensive operations for the same key!
\end{lstlisting}

\subsection{Real-World Impact}

In production systems, this problem manifests as:

\begin{itemize}
\item \textbf{Backend Overload}: Multiple identical expensive queries
      hitting the database
\item \textbf{Resource Waste}: CPU and memory consumed by redundant
      computations
\item \textbf{Latency Amplification}: All threads wait for their
      individual computations
\item \textbf{Cascade Failures}: Backend systems overwhelmed by
      duplicate requests
\end{itemize}

\subsection{The Challenge: Thread Coordination}

The solution requires careful coordination where:

\begin{enumerate}
\item \textbf{One thread computes}: Only the first thread should execute
      the expensive operation
\item \textbf{Others wait}: Subsequent threads must wait for the first
      thread's result
\item \textbf{All get the result}: Once computed, all waiting threads
      receive the same value
\item \textbf{Handle failures}: If computation fails, threads shouldn't
      wait indefinitely
\end{enumerate}

\subsection{Entry States}

Each cache entry maintains one of five possible states that coordinate
thread access and lifecycle management:

\begin{itemize}
\item \textbf{EMPTY}: Slot available for a new key; no data associated.
\item \textbf{COMPUTING}: Data being computed by the miss solver (thundering herd protection).
\item \textbf{READY}: Valid positive data available (within TTL).
\item \textbf{FAILED}: Computation failed; negative result cached (within negative TTL).
\item \textbf{INVALIDATED}: Logically removed; prioritized for LRU eviction but memory-safe for active waiters.
\end{itemize}

\section{Critical Concurrency Challenges}

\subsection{Variadic API and Perfect Forwarding}

The core primitive \texttt{get\_or\_compute} has been evolved into a
variadic template that supports arbitrary context propagation:

\begin{lstlisting}[caption=Variadic API with Perfect Forwarding]
template <typename Key, typename Value, typename... Args>
CacheResult<Value> get_or_compute(const Key &key, Args... args) {
    return resolve_miss(entry, now, !existed, std::forward<Args>(args)...);
}
\end{lstlisting}

This allows users to pass opaque parameters (e.g., database connections, 
transaction IDs) directly to the miss solver in a 100\% type-safe manner 
without runtime overhead.

\subsection{Lock-Free Performance Metrics}

To minimize global lock contention, cache statistics were moved from a 
protected struct to individual atomic counters (\lstinline|std::atomic<size_t>|). 
This enables the "fast path" (cache hits) to operate without acquiring the 
global mutex, significantly increasing throughput under massive concurrency.

\subsection{The Double-Checked Locking Problem}

A common but problematic pattern in cache implementations is:

\begin{lstlisting}[caption=Problematic synchronization pattern]
cache_lock.lock();
if (hash_table.find(key) != end) {
    entry_ptr = hash_table[key];
    entry_ptr->mutex.lock();
    cache_lock.unlock();  // PROBLEM!
    
    // What if Thread 2 evicts this entry?
}
\end{lstlisting}

The problem arises when the main lock is released before finishing with
the entry.

\section{Implemented Solutions}

\subsection{Fine-Grained Synchronization: The Core Mechanism}

The solution to the thundering herd problem relies on \textbf{per-entry
synchronization} using a mutex and condition variable for each cache
entry, combined with entry states.

\subsubsection{Why Per-Entry Locks?}

A single global mutex would serialize all cache access, destroying
concurrency:

\begin{lstlisting}[caption=Naive approach with single mutex]
mutex global_mutex;

Data get(Key k) {
    lock_guard lock(global_mutex);  // Only ONE thread at a time!
    
    if (hash_table.contains(k)) {
        return hash_table[k];
    }
    
    Data result = expensive_computation(k);
    hash_table[k] = result;
    return result;
}
\end{lstlisting}

With 100K req/sec, a global lock would create a massive bottleneck.

\subsubsection{The Solution: Per-Entry Mutex + Condition Variable}

Each cache entry has its own synchronization primitives:

\begin{lstlisting}[caption=Per-entry synchronization primitives]
struct CacheEntry {
    Key key;
    Data data;
    
    // Synchronization primitives - ONE PER ENTRY
    mutex mtx;
    condition_variable waiting_cv;
    
    Status status;
    time_point<steady_clock> ttl_exp_time;
};
\end{lstlisting}

\subsubsection{The Wait/Notify Pattern}

When multiple threads request the same key simultaneously:

\begin{algorithm}[H]
\caption{Thread Coordination for Same Key}
\begin{algorithmic}[1]
\STATE \textbf{Thread 1} arrives first:
\STATE \quad Acquires cache mutex
\STATE \quad Creates entry with status = CALCULATING
\STATE \quad Releases cache mutex
\STATE \quad Executes expensive computation
\STATE \quad Sets status = READY
\STATE \quad Calls notify\_all() to wake waiters
\STATE
\STATE \textbf{Threads 2, 3, ..., N} arrive during computation:
\STATE \quad Acquire cache mutex
\STATE \quad Find entry with status = CALCULATING
\STATE \quad Call wait() and BLOCK
\STATE \quad Wake up when notified
\STATE \quad Read the computed result
\end{algorithmic}
\end{algorithm}

\subsection{Hierarchical Synchronization Pattern}

\begin{algorithm}
\caption{Safe Synchronization Pattern}
\begin{algorithmic}[1]
\STATE Acquire cache\_mutex
\STATE Search for entry in hash\_table
\IF{entry found}
    \STATE Acquire entry\_mutex
    \STATE Release cache\_mutex
    \STATE Work with entry
    \STATE Release entry\_mutex
\ELSE
    \STATE Create new entry
    \STATE Acquire entry\_mutex
    \STATE Release cache\_mutex
    \STATE Process entry
    \STATE Release entry\_mutex
\ENDIF
\end{algorithmic}
\end{algorithm}

\subsection{ABA Problem Prevention and Memory Safety}

The ABA problem and use-after-free risks are prevented by a tiered
ownership model:

\begin{enumerate}
\item \textbf{Internal Refcounts}: Each \texttt{CacheEntry} maintains an
      atomic reference counter.
\item \textbf{EntryGuard (RAII)}: A specialized guard acquires a 
      reference upon entry lookup and releases it upon scope exit.
\item \textbf{Shared Pointers}: The actual \texttt{Value} is managed 
      via \texttt{std::shared\_ptr}.
\end{enumerate}

This ensures that even if an entry is evicted from the hash table or 
invalidated while a thread is computing its value, the entry's memory 
remains stable until the last thread finishes its operation.

\section{Public API}

The cache exposes a rich API beyond the core \texttt{get\_or\_compute} method.
All methods are thread-safe and respect the single-flight semantics.

\subsection{Result Types}

All lookup operations return a \texttt{CacheResult<Value>} that distinguishes
the origin of the result:

\begin{itemize}
\item \textbf{HitPositive}: Value found in cache (valid positive entry)
\item \textbf{HitNegative}: Cached failure found (valid negative entry)
\item \textbf{ComputedPositive}: Miss solver returned a value (newly computed)
\item \textbf{ComputedNegative}: Miss solver returned nullptr (newly failed)
\item \textbf{Saturated}: Cache full with all entries in Computing state
\end{itemize}

This allows callers to implement telemetry based on cache behavior.

\begin{lstlisting}[caption=Lookup API signatures]
// Primary: compute on miss, wait if Computing
CacheResult<Value> get_or_compute(const Key &key, Args... args);

// Read-only: wait if Computing, never triggers solver
std::optional<CacheResult<Value>> find(const Key &key);

// Non-blocking: returns nullopt if entry busy or missing
std::optional<CacheResult<Value>> peek(const Key &key);

// Fast existence check
bool has(const Key &key);
\end{lstlisting}

\subsection{Mutation Methods}

\begin{lstlisting}[caption=Mutation API signatures]
// Marks entry as Invalidated, moves to LRU tail for priority eviction.
// Returns false if key not found or entry is Computing.
bool invalidate(const Key &key);

// Refreshes TTL and moves to MRU. Returns false if expired or missing.
bool touch(const Key &key);
\end{lstlisting}

\textbf{Key design decisions}:
\begin{itemize}
\item \texttt{invalidate()} refuses to invalidate \texttt{Computing} entries to
      avoid interrupting ongoing computations.
\item \texttt{touch()} implements sliding-window TTL: each access extends the
      entry's lifetime by the full TTL duration.
\item All methods use \texttt{EntryGuard} RAII to safely handle concurrent
      eviction during the operation.
\end{itemize}

\section{Formal Verification}

\subsection{Model Architecture (v5)}

The cache is formally verified using SPIN with a Promela model that faithfully
captures the C++ synchronization semantics. The model includes:

\begin{itemize}
\item \textbf{Explicit Refcount}: \texttt{slot\_rc[]} models \texttt{CacheEntry::\_refcount}
      and \texttt{EntryGuard} RAII lifetime.
\item \textbf{TTL Aging}: \texttt{slot\_age[]} with threshold models TTL refresh on hit.
\item \textbf{Three-Phase Locking}: Phase 1 (global lock), Phase 2 (solver), 
      Phase 3 (entry lock + CV wait).
\item \textbf{All Public API}: Separate processes model \texttt{get\_or\_compute},
      \texttt{find}, \texttt{invalidate}, \texttt{touch}, and \texttt{peek}.
\end{itemize}

\subsection{Bug Found by Formal Verification}

The model revealed a critical bug in \texttt{find\_evictable\_lru()}:
the C++ code did not check the refcount before eviction, allowing entries
held by active \texttt{EntryGuard} instances to be evicted, causing
potential use-after-free.

\begin{lstlisting}[caption=Bug fix identified by formal model]
// BEFORE (bug): eviction possible with active holders
if (entry->state() != EntryState::Computing)
  return entry;

// AFTER (fix): aligned with Promela invariant slot_rc[s] <= 1
if (entry->state() != EntryState::Computing &&
    entry->_refcount.load(std::memory_order_acquire) <= 1)
  return entry;
\end{lstlisting}

This demonstrates the value of formal verification: the model's
\texttt{slot\_rc[s] <= 1} guard in eviction was already correct,
exposing the missing check in the C++ implementation.

\begin{enumerate}

\item \textbf{Negative TTL + Circuit Breaker}: Essential for preventing cascades
\item \textbf{Real-time Metrics}: Fundamental for debugging
\item \textbf{Memory Management}: Prevents OOM kills in Kubernetes
\item \textbf{Failover is the Weak Link}: Highest operational risk

\begin{itemize}

\item \textbf{Backend Protection}: Circuit breakers mitigate saturation
\item \textbf{Graceful Degradation}: System maintains basic functionality
\end{itemize}

The presented implementation successfully solves the main challenges of

\section{Promela Model for Formal Verification}

\subsection{Model Overview (v5)}

The Promela model (\texttt{formal/cache\_model.pml}) provides exhaustive
verification of the cache's concurrency semantics. Key characteristics:

\begin{itemize}
\item \textbf{Capacity}: 2 slots, 3 keys, 6 request threads + 4 background processes
\item \textbf{State vector}: 152 bytes
\item \textbf{State space}: $\sim$3.5 million states explored exhaustively
\item \textbf{Verification time}: $\sim$4 seconds on modern hardware
\end{itemize}

\subsection{What is Modeled}

\begin{itemize}
\item \textbf{Refcount semantics}: \texttt{slot\_rc[]} faithfully models 
      \texttt{CacheEntry::\_refcount} and \texttt{EntryGuard} RAII
\item \textbf{TTL aging}: \texttt{slot\_age[]} with \texttt{AGE\_THRESHOLD} 
      models sliding-window TTL refresh
\item \textbf{All public API}: \texttt{get\_or\_compute}, \texttt{find}, 
      \texttt{invalidate}, \texttt{touch}, \texttt{peek}
\item \textbf{LRU eviction}: With refcount guard (\texttt{rc <= 1})
\item \textbf{Three-phase locking}: Global lock $\to$ solver $\to$ entry lock
\item \textbf{CV wait semantics}: Non-owners block on Computing entries
\end{itemize}

\subsection{What is Abstracted}

\begin{itemize}
\item Exact wall-clock timing (replaced by discrete aging steps)
\item Hash table collision resolution details
\item Value content (only state transitions matter)
\item Circuit breaker integration
\end{itemize}

\subsection{Verification Value}

The model proved its worth by discovering a real bug: the C++ 
\texttt{find\_evictable\_lru()} was missing the refcount check that the
model already enforced. This demonstrates that formal verification
catches bugs that escape code review and testing.

Production testing at 100K req/sec complements formal verification by
validating performance under realistic loads.
